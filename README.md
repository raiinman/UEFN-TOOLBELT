## Known Issue — UEFN 42.00 MCP Toolsets

**If Toolbelt stops loading on startup, this is almost certainly why.**

Enabling **Project Settings → Beta Access → UEFN MCP Toolsets** prevents your
project's `Content/Python/init_unreal.py` from running, so Toolbelt never starts.

Nothing errors and nothing is logged. The tool count is 1 instead of 362 and
every `tb.run(...)` answers `Unknown tool`, which looks like a Toolbelt bug and
is not one.

**Cause.** Epic's Toolsets plugins force-enable Python during editor init, about
100 frames *before* UEFN mounts your project plugin. Your `init_unreal.py` is not
scanned because the plugin containing it has not loaded yet. Verified by diffing
editor logs across boots with the flag on and off — see `docs/UEFN_QUIRKS.md` #36.

**Workaround.** Either turn the flag off, or run this once per editor session:

<table align="center"><tbody><tr><td align="left"><pre><code class="language-python">import UEFN_Toolbelt as tb; tb.register()&#10;</code></pre></td></tr></tbody></table>



That recovers all 362 tools and the dashboard (`tb.launch_qt()`). It does not
make a top-bar menu appear: menu entries register on 42.00 and still never
render. Epic's MCP continues to work either way; only Toolbelt's auto-start is
affected.

`tb.smoke_test()` detects this and names it, so you are never left guessing.

**Status.** Not fixable from Toolbelt: `PythonScriptPluginSettings` is not exposed
to Python on this build, and UEFN projects have no `Config/` directory for an
explicit startup-script entry. It needs an Epic-side fix.

## ⚠️ Automated Integration Testing

The smoke test checks registration only: a minimum registry count (179) and six named tools; it executes no tool and validates no schema. The integration test verifies that they *work* — in a live UEFN editor, against real actors.

<a name="readme-section-11"></a>

### What the integration test actually does

`toolbelt_integration_test` is a fixture-driven test harness that runs inside UEFN:

<table align="center"><tbody><tr><td align="center">1</td><td align="center"><strong>Spawns</strong> temporary cube/sphere actors programmatically</td></tr><tr><td align="center">2</td><td align="center"><strong>Selects</strong> them via <code>EditorActorSubsystem</code></td></tr><tr><td align="center">3</td><td align="center"><strong>Runs</strong> each tool against that live selection</td></tr><tr><td align="center">4</td><td align="center"><strong>Verifies</strong> the result — property changed, actor spawned, file written, count correct</td></tr><tr><td align="center">5</td><td align="center"><strong>Cleans up</strong> every actor it touched via a single undo transaction</td></tr></tbody></table>


**190 checks across 362 tools — 190/190 passing live on UEFN 42.00** — covering materials, bulk ops, patterns, scatter, splines, snapshots, asset management, Verse tools, screenshots, LODs, arena, measurement, localization, zones, stamps, actor org, proximity placement, advanced alignment, signs, post-process, audio, level health, config, lighting, and world state.

Of those 190, **163 verify a real outcome** — a property changed, a file written,
an actor count, a tag read back — and **27 are execution-only**: they prove the
tool ran without raising, nothing more. Both numbers are reported by the suite
on every run, because a headline "190/190" that silently includes checks which
cannot fail overstates what the suite knows. That is not hypothetical: a fully
green run once hid a wrong-rotation-axis bug ([Quirk #41](docs/UEFN_QUIRKS.md))

## Key Systems — How They Work

<a name="readme-section-26"></a>

### 1. The Tool Registry

Every tool self-registers with a one-line decorator. The registry is a singleton shared
across the entire session.

<table align="center"><tbody><tr><td align="left"><pre><code class="language-python">from UEFN_Toolbelt.registry import register_tool&#10;&#10;@register_tool(&#10;    name="my_tool",&#10;    category="Procedural",&#10;    description="Does something amazing",&#10;    tags=["procedural", "spawn"],&#10;)&#10;def run(**kwargs) -&gt; dict:&#10;    ...&#10;    return {"status": "ok", "count": placed}&#10;</code></pre></td></tr></tbody></table>



Calling `tb.run("my_tool")` from anywhere — REPL, Blueprint node, another tool — routes
through the registry with full error containment. A crashing tool never kills your session.

Every tool returns a structured `dict` with at minimum a `"status"` key. This is the
**MCP Return Contract**: AI agents calling tools via the bridge read the return dict directly
from the JSON response. Zero log parsing required.

## Math & Performance Scaling

To prevent the editor from hanging during mass operations, Toolbelt uses
`unreal.ScopedSlowTask` — a native UE progress dialog with cancel support.

<a name="readme-section-36"></a>

### Complexity Formula

For an operation across $A$ actors with $M$ material slots each:

$$\text{Complexity} = O(A + (A \times M))$$

<a name="readme-section-37"></a>

### Chunked Execution Pattern

<table align="center"><tbody><tr><td align="left"><pre><code class="language-python"># From core.py — wrap any iterable:&#10;with with_progress(actors, "Applying materials") as bar_iter:&#10;    for actor in bar_iter:&#10;        _apply_preset_to_actor(actor, preset, "Chrome")&#10;        # ScopedSlowTask advances one step per actor&#10;        # User can cancel mid-way — no partial corrupt state&#10;</code></pre></td></tr></tbody></table>



The progress bar displays a cancel button. Cancellation is handled gracefully; already-
processed actors retain their changes (inside the transaction, so all-or-nothing undo
still works at the outer level).

### MCP Bridge (4)

Start the listener in UEFN, then an authenticated same-user MCP client can run
the registered catalogue by name and operate the editor through queued
main-thread dispatch. Listener start/stop/restart remain local-only controls.
Arbitrary remote Python is unavailable and cannot be enabled with the former
`UEFN_TOOLBELT_MCP_ALLOW_EXECUTE_PYTHON` variable. Deliberate scripting remains

### Step 1 — Enable Python in UEFN

### Step 2 — Install PySide6 (one-time, required for the dashboard UI)

Open a **regular Windows terminal** — not inside UEFN — and run:

<table align="center"><tbody><tr><td align="left"><pre><code class="language-bat">"C:\Program Files\Epic Games\Fortnite\Engine\Binaries\ThirdParty\Python3\Win64\python.exe" -m pip install PySide6&#10;</code></pre></td></tr></tbody></table>



<blockquote align="center">

</blockquote>



If the path above doesn't exist, find it at:
<table align="center"><tbody><tr><td align="left"><pre><code>C:\Program Files\Epic Games\Fortnite\Engine\Binaries\ThirdParty\Python3\Win64\python.exe&#10;</code></pre></td></tr></tbody></table>

## Adding a New Tool

**3 steps. No boilerplate. No registration config.**

**Step 1** — Create `Content/Python/UEFN_Toolbelt/tools/my_tool.py`:

<table align="center"><tbody><tr><td align="left"><pre><code class="language-python">"""UEFN TOOLBELT — My Tool"""&#10;import unreal&#10;from ..core import undo_transaction, require_selection, log_info&#10;from ..registry import register_tool&#10;&#10;@register_tool(&#10;    name="my_tool",&#10;    category="Utilities",&#10;    description="Does something amazing",&#10;    tags=["utility", "amazing"],&#10;)&#10;def run(**kwargs) -&gt; dict:&#10;    actors = require_selection()&#10;    if actors is None:&#10;        return {"status": "error", "count": 0}&#10;    with undo_transaction("My Tool"):&#10;        for actor in actors:&#10;            log_info(f"Processing {actor.get_actor_label()}")&#10;            # your logic here&#10;    return {"status": "ok", "count": len(actors)}&#10;</code></pre></td></tr></tbody></table>



<blockquote align="center">
<p align="center"><strong>Return contract:</strong> Every tool must return a <code>dict</code> with a <code>"status"</code> key. This is what
makes tools readable by AI agents via the MCP bridge — they read <code>result["status"]</code> and
domain keys like <code>"count"</code> or <code>"path"</code> directly from the JSON response. Never return <code>None</code>.</p>
</blockquote>



**Step 2** — Add one line to `tools/__init__.py`:

<table align="center"><tbody><tr><td align="left"><pre><code class="language-python">from . import my_tool&#10;</code></pre></td></tr></tbody></table>



**Step 3** — Add a menu entry in `init_unreal.py`'s `_build_toolbelt_menu()` (optional):

<table align="center"><tbody><tr><td align="left"><pre><code class="language-python">_add_entry(tb_sub, "Utilities", "MyTool",&#10;           "My Tool", "Does something amazing",&#10;           "import UEFN_Toolbelt as tb; tb.run('my_tool')")&#10;</code></pre></td></tr></tbody></table>



Your tool is now registered, searchable, undo-safe, and reachable from the dashboard
and `tb.run("my_tool")`.

## Custom Plugins & Security

UEFN Toolbelt is a **security-first extensible platform**. Third-party developers can create custom tools that automatically load into the Dashboard and AI bridge — but the Toolbelt enforces strict sandboxing to protect your editor and project files.

<a name="readme-section-95"></a>

### How Custom Plugins Work

Drop a `.py` file into `[Your Project]/Saved/UEFN_Toolbelt/Custom_Plugins/`. The Toolbelt will:
<table align="center"><tbody><tr><td align="center">1</td><td align="center"><strong>Discover</strong> the file on startup.</td></tr><tr><td align="center">2</td><td align="center"><strong>Security-screen</strong> it through four gates (see below).</td></tr><tr><td align="center">3</td><td align="center"><strong>Register</strong> it in the tool registry with a UI button and AI accessibility.</td></tr><tr><td align="center">4</td><td align="center"><strong>Log</strong> a tamper-evident audit record.</td></tr></tbody></table>


<table align="center"><tbody><tr><td align="left"><pre><code class="language-python"># Example: one-file custom plugin&#10;from UEFN_Toolbelt.registry import register_tool&#10;from UEFN_Toolbelt import core&#10;&#10;@register_tool(name="my_tool", category="Community", description="Does something cool")&#10;def run(**kwargs) -&gt; dict:&#10;    core.log_info("My custom tool ran!")&#10;    return {"status": "ok"}   # always return a dict&#10;</code></pre></td></tr></tbody></table>



<a name="readme-section-96"></a>

### 🔒 Four-Gate Security Model

Every plugin passes through **four security gates** before it can execute inside your editor:

<table align="center">
<thead>
<tr>
<th align="center">Gate</th>
<th align="center">What It Checks</th>
<th align="center">What Happens If It Fails</th>
</tr>
</thead>
<tbody>
<tr>
<td align="center"><strong>1. File Size Limit</strong></td>
<td align="center">Rejects files &gt; 50 KB</td>
<td align="center">Blocks obfuscated or suspiciously large payloads</td>
</tr>
<tr>
<td align="center"><strong>2. AST Import Scanner</strong></td>
<td align="center">Parses the source code <em>without executing it</em> using Python's <code>ast</code> module</td>
<td align="center">Blocks dangerous imports: <code>subprocess</code>, <code>socket</code>, <code>ctypes</code>, <code>shutil</code>, <code>http</code>, <code>urllib</code>, <code>requests</code>, <code>webbrowser</code>, <code>smtplib</code>, <code>ftplib</code>, <code>xmlrpc</code>, <code>multiprocessing</code>, <code>signal</code>, <code>_thread</code></td>
</tr>
<tr>
<td align="center"><strong>3. Namespace Protection</strong></td>
<td align="center">Checks if the tool name collides with a core Toolbelt tool</td>
<td align="center">Rejects registration — prevents hijacking of system commands like <code>toolbelt_smoke_test</code></td>
</tr>
<tr>
<td align="center"><strong>4. SHA-256 Integrity Hash</strong></td>
<td align="center">Computes a cryptographic fingerprint of every loaded plugin</td>
<td align="center">Logged to <code>plugin_audit.json</code> — detect tampering by comparing hashes across sessions</td>
</tr>
</tbody>
</table>



<a name="readme-section-97"></a>

### 📋 Plugin Audit Log

Every time the Toolbelt boots, it writes a tamper-evident audit trail to:
<table align="center"><tbody><tr><td align="left"><pre><code>Saved/UEFN_Toolbelt/plugin_audit.json&#10;</code></pre></td></tr></tbody></table>



Each entry records the plugin name, its SHA-256 hash, file size, load status, and timestamp. If a plugin file changes between sessions, the hash changes — making unauthorized modifications instantly detectable.

## ⚠️ Critical: The "Main Thread Lock" Quirk

Because UEFN runs Python on the **main render thread**, there is a unique deadlock behavior you must avoid:

<table align="center"><tbody><tr><td align="center"><strong>Async APIs</strong>: Commands like <code>take_high_res_screenshot</code> or background asset saves are queued for the <strong>next frame</strong>.</td></tr><tr><td align="center"><strong>The Deadlock</strong>: If your Python script uses <code>time.sleep()</code> or a long loop to "wait" for a file to appear, you are <strong>blocking the main thread</strong>. Unreal cannot finish the current frame, so it will <strong>never write the file</strong> while your script is waiting.</td></tr><tr><td align="center"><strong>The Solution</strong>: Trigger the action and exit. Do not attempt to verify file existence in the same execution block if the engine needs to tick to produce that file.</td></tr></tbody></table>

## MCP — Connect an AI Client to UEFN

UEFN Toolbelt ships a two-process MCP (Model Context Protocol) architecture:
`mcp_server.py` is an MCP stdio server intended for clients such as Claude Code,
Codex, or Cursor, and it forwards registered commands to the editor through
Toolbelt's authenticated custom bridge.

**MCP-host integration is untested since the security hardening.**
No accepted record has run `mcp_server.py` through any MCP host, stdio, or FastMCP since the WO-001 authentication and WO-004 transport changes; earlier compatibility statements predate them. See the
[evidence gaps](docs/OFFICIAL_MCP_AND_TOOLBELT.md#evidence-gaps). Claude Code
loads `CLAUDE.md`, and Codex and Cursor load `AGENTS.md`, so an agent that does
connect starts with this codebase's context.

**How it works:**

<table align="center"><tbody><tr><td align="left"><pre><code>Your AI  ←── MCP stdio ──→  mcp_server.py  ←── authenticated loopback ──→  UEFN&#10;  (IDE)                       (same user)                         (mcp_bridge.py)&#10;</code></pre></td></tr></tbody></table>



**One-time setup:**
<table align="center"><tbody><tr><td align="left"><pre><code class="language-bat">pip install mcp&#10;</code></pre></td></tr></tbody></table>



**Start the listener in UEFN:**
<table align="center"><tbody><tr><td align="left"><pre><code class="language-python">import UEFN_Toolbelt as tb; tb.run("mcp_start")&#10;# Output Log: [MCP] ✓ Listener running on http://127.0.0.1:8765&#10;</code></pre></td></tr></tbody></table>



If **UEFN MCP Toolsets** is enabled and `mcp_start` reports that Toolbelt is not
registered, recover once after each full editor start before starting the
listener (known Quirk #36):

<table align="center"><tbody><tr><td align="left"><pre><code class="language-python">import UEFN_Toolbelt as tb; tb.register(); tb.run("mcp_start")&#10;</code></pre></td></tr></tbody></table>



`.mcp.json` is not tracked: copy `.mcp.json.template` to the gitignored
`.mcp.json` and set the absolute path to `mcp_server.py` (Getting Started, Step 8).
The listener creates a rotating same-user session handoff under
`Saved/UEFN_Toolbelt/`; `mcp_server.py` reads it automatically. Restart rotates
the secret and stop removes it. The secret is never printed or returned.

**What a connected client can do:**
<table align="center"><tbody><tr><td align="center">Run registered Toolbelt tools by name (<code>run_toolbelt_tool</code>), except local-only
listener lifecycle controls</td></tr><tr><td align="center">Spawn, move, delete actors; read selected actors live</td></tr><tr><td align="center">List, rename, duplicate, import, delete Content Browser assets</td></tr><tr><td align="center">Create material instances with parameters</td></tr><tr><td align="center">Batch multiple operations in a single editor tick</td></tr><tr><td align="center">Undo / redo editor actions</td></tr><tr><td align="center">Read command history with per-command timing</td></tr><tr><td align="center">Control the viewport camera</td></tr><tr><td align="center">Generate spec-accurate Verse code (see below)</td></tr></tbody></table>


Arbitrary remote Python is unavailable through the Toolbelt bridge. Use a
registered command for remote automation or the local UEFN Python console for
deliberate in-editor scripting.

**External client — works with any AI, any language:**

`client.py` in the project root is a stdlib-only client for trusted same-user
automation. It loads the current session handoff and authenticates every request:

<table align="center"><tbody><tr><td align="left"><pre><code class="language-python">from client import ToolbeltClient&#10;&#10;ue = ToolbeltClient()&#10;ue.ping()&#10;ue.run_tool("scatter_hism", count=200, radius=4000.0)&#10;actors = ue.get_all_actors()&#10;ue.batch([&#10;    {"command": "run_tool", "params": {"tool_name": "snapshot_save"}},&#10;    {"command": "save_current_level", "params": {}},&#10;])&#10;</code></pre></td></tr></tbody></table>



Raw unauthenticated HTTP, browser requests, CORS preflight, remote hosts, and
cross-machine CI are rejected. A non-Python local client must deliberately
implement the same protected handoff and bearer-header contract. Treat the
handoff as privileged editor-control material; loopback is not a sandbox and a
compromised process running as the same Windows user may be able to read it.

**Host compatibility is unconfirmed for this release.** No MCP host — Claude
Code, Codex, Cursor, or another — has been exercised against the hardened
`mcp_server.py`; `client.py` direct calls are the path with recorded live
evidence, on one UEFN 42.20 boot. Claude Code additionally auto-loads `CLAUDE.md` on open, which is why the autonomous-build walkthrough above uses it — Codex and Cursor get the same context from `AGENTS.md`.

MCP bridge architecture inspired by [Kirch's uefn-mcp-server](https://github.com/KirChuvakov/uefn-mcp-server) ([@KirchCreator](https://x.com/KirchCreator)) — full credit for the queue + Slate tick pattern.

## Spec-Accurate Verse Code Generation

Before generating any code, Claude queries the spec for exact syntax, effect specifiers, and API signatures. The generated code is spec-accurate, not template-accurate.

### v2.5.0 — October 2026 (Hardened bridge, honest coverage, official-MCP truth)

**Why this matters:** Toolbelt's custom bridge used to accept unauthenticated

## Why the Theme System Matters

Most tools hard-code their colors. When a new window is built, the developer copy-pastes hex values and the UI slowly drifts — different shades of dark, slightly different borders, inconsistent accent colors. Community plugins make it worse because plugin authors have no reference to match.

The Toolbelt theme system solves this structurally, not just with documentation:

<table align="center"><tbody><tr><td align="center"><strong><code>core/theme.py</code> is the single source of truth.</strong> <code>PALETTE</code> is a live dict. Every color in the platform — dashboard, tool windows, device graph, community plugins — reads from it. Change one value and every window updates on the next reload.</td></tr><tr><td align="center"><strong><code>set_theme()</code> updates everything live.</strong> It mutates <code>PALETTE</code> in-place, rebuilds the QSS stylesheet, and notifies every subscribed window via a callback list. No restart needed. This is exactly how Discord, VS Code, and Obsidian implement live theme switching.</td></tr><tr><td align="center"><strong><code>ToolbeltWindow</code> enforces the standard automatically.</strong> Subclassing <code>ToolbeltWindow</code> instead of <code>QMainWindow</code> means your window gets the theme applied, subscribes to future changes, and unsubscribes cleanly on close — for free. Plugin authors get platform-consistent UI without knowing how the theme system works.</td></tr><tr><td align="center"><strong>Community plugins inherit theming.</strong> A plugin that subclasses <code>ToolbeltWindow</code> will switch themes with the rest of the platform automatically. The platform grows without visual fragmentation.</td></tr><tr><td align="center"><strong>6 built-in themes</strong> (<code>toolbelt_dark</code>, <code>midnight</code>, <code>ocean</code>, <code>nord</code>, <code>forest</code>, <code>daylight</code>) — switchable from the Appearance tab, <code>tb.run("theme_set", name="ocean")</code>, or MCP. Persists across restarts via <code>config.json</code>.</td></tr></tbody></table>


This is what separates a collection of scripts from a platform.

## Contributing

Contributions are welcome and encouraged. This project follows a simple rule: **keep it useful for real UEFN creators.**

<blockquote align="center">
<p align="center"><strong>Testing your tools:</strong> Before contributing, please read <a href="TOOL_STATUS.md">TOOL_STATUS.md</a> to understand which tools are covered by automated tests and which require manual verification.</p>
</blockquote>



<a name="readme-section-154"></a>

### How to contribute

<table align="center"><tbody><tr><td align="center">1</td><td align="center"><strong>Fork</strong> the repo and create a branch: <code>git checkout -b feature/my-tool</code></td></tr><tr><td align="center">2</td><td align="center"><strong>Follow the tool structure</strong> — see <a href="#adding-a-new-tool">Adding a New Tool</a> for the exact pattern</td></tr><tr><td align="center">3</td><td align="left"><strong>Test in a live UEFN editor — this is mandatory.</strong> Syntax checks don't catch UEFN runtime failures. Run the hard-refresh bundle in the UEFN Python console and confirm your tool works:<pre><code class="language-python">import sys; [sys.modules.pop(k) for k in list(sys.modules) if "UEFN_Toolbelt" in k]; import UEFN_Toolbelt as tb; tb.register_all_tools(); tb.run("your_tool_name")&#10;</code></pre>
Then run the smoke test to confirm no regressions: <code>tb.run("toolbelt_smoke_test")</code></td></tr><tr><td align="center">4</td><td align="center"><strong>Open a Pull Request</strong> with a clear description of what the tool does and why it belongs here</td></tr></tbody></table>


<a name="readme-section-155"></a>

### Guidelines

<table align="center"><tbody><tr><td align="center">Every tool must be wrapped in <code>ScopedEditorTransaction</code> if it modifies the level — one Ctrl+Z must undo it</td></tr><tr><td align="center">No network calls. Tools that need external data should require the user to provide it as a parameter</td></tr><tr><td align="center">No new dependencies beyond <code>unreal</code> (built-in) and <code>PySide6</code> (already required for the dashboard)</td></tr><tr><td align="center">Tool names use <code>snake_case</code>. Category names use <code>Title Case</code>. Both must be unique</td></tr><tr><td align="center">Add your tool to the smoke test if it has a meaningful self-test</td></tr><tr><td align="center">If you fix a UEFN API incompatibility, document what the correct API is in a comment — the API is underdocumented and your discovery helps everyone</td></tr></tbody></table>


<a name="readme-section-156"></a>

### Code style

<table align="center"><tbody><tr><td align="center">Follow the existing patterns in <code>tools/</code> — no need for docstrings on every line, but the <code>@register_tool</code> description must be clear enough for the search box</td></tr><tr><td align="center">Python 3.11 compatible — no f-string backslashes, no 3.12+ syntax</td></tr><tr><td align="center">All paths use <code>unreal.Paths</code> or <code>os.path</code> — no hardcoded Windows separators</td></tr></tbody></table>

## Tool Requests

Have an idea for a tool that should be in the Toolbelt? Open a GitHub Issue with the label **`tool-request`**.

**Good tool request format:**

<table align="center"><tbody><tr><td align="left"><pre><code>Title: [Tool Request] Bulk set collision preset on selected actors&#10;&#10;What it does:&#10;  Sets the collision preset (e.g. BlockAll, OverlapAll, NoCollision) on all&#10;  selected static mesh actors in one click.&#10;&#10;Why it's useful:&#10;  Setting collision on 50 props one at a time in Details is extremely slow.&#10;  This is one of the most common repeated tasks in UEFN prop placement.&#10;&#10;Category: Bulk Ops&#10;Tags: collision, bulk, static mesh&#10;</code></pre></td></tr></tbody></table>



The more specific you are about the exact UEFN operation and why it saves time, the more likely it is to ship.
